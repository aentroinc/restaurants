# Release Runbook (Foundry Apollo equivalent)

Manage releases as immutable bundles that are promoted across environments
(`dev` -> `staging` -> `prod`) with automatic rollback on health-check failure.

## Concepts

- **Bundle**: a JSON manifest pinning a specific git SHA, image tags
  (backend / frontend), the helm values file hash, and the alembic migration
  list. Generated by `infra/scripts/bundle.sh` and uploaded as a GH Actions
  artifact named `aentro-bundle-<sha>`.
- **Promote**: copy that exact bundle to the next environment by re-tagging
  the ECR image and updating the ECS service / task definition. No rebuild.
- **Rollback**: point the ECS service back to a previous task-definition
  revision (matched by image tag = previous SHA, or "previous").

## Environments

| Env     | Cluster           | URL                  | Helm values                  | Terraform                  |
| ------- | ----------------- | -------------------- | ---------------------------- | -------------------------- |
| dev     | aentro-dev        | https://dev.aentro.io     | `charts/aentro/values.dev.yaml`     | `infra/environments/dev`    |
| staging | aentro-staging    | https://staging.aentro.io | `charts/aentro/values.staging.yaml` | `infra/environments/staging`|
| prod    | aentro-prod       | https://app.aentro.io     | `charts/aentro/values.prod.yaml`    | `infra/environments/prod`   |

## Standard release flow

1. **Build** (automatic on push to `main`)
   - Workflow: `.github/workflows/build.yml`
   - Builds backend & frontend images, pushes to ECR with tag `<sha>` and the
     moving tag `staging`.
   - Generates `aentro-bundle-<sha>.json` artifact (90 day retention).

2. **Promote dev -> staging** (auto on push by virtue of the moving `staging`
   tag, or manual via the Promote workflow)
   - Workflow: `.github/workflows/promote.yml`
   - Inputs: `from_env=dev`, `to_env=staging`, `sha=<short-sha>`.
   - Runs `db-migrate.yml` first, then `infra/scripts/promote.sh`, then
     `healthcheck.sh` against `https://staging.aentro.io/api/v1/admin/health`.

3. **Smoke test on staging**
   - `make smoke ENV=staging` (calls `healthcheck.sh`).
   - Manual UAT against https://staging.aentro.io.

4. **Promote staging -> prod**
   - Workflow: `.github/workflows/promote.yml`
   - Inputs: `from_env=staging`, `to_env=prod`, `sha=<short-sha>`.
   - Health-check window: 5 minutes (30 attempts x 10s). Failure triggers
     `rollback.sh prod previous`.

5. **Manual rollback** (if a regression is found later)
   - Workflow: `.github/workflows/rollback.yml`
   - Inputs: `env=prod`, `target_sha=<known-good-sha>`.

## Local dry-run

All scripts honour `DRYRUN=1`, which replaces every `aws` invocation with
`echo`, so they can be exercised with no AWS credentials.

```bash
# Bundle metadata
SHA=$(git rev-parse --short HEAD) make bundle

# Promote dev -> staging in dry-run mode
DRYRUN=1 make promote FROM=dev TO=staging SHA=$(git rev-parse --short HEAD)

# Rollback prod to a specific SHA in dry-run mode
DRYRUN=1 make rollback ENV=prod SHA=abc1234

# Healthcheck
make smoke ENV=staging
```

## Required GitHub secrets

| Secret name              | Used by                             |
| ------------------------ | ----------------------------------- |
| `AWS_DEPLOY_ROLE_ARN`    | All workflows (OIDC role assumption) |
| `AWS_ACCOUNT_ID`         | promote.yml                         |
| `ECR_REGISTRY`           | build.yml, promote.yml              |
| `DEV_NETWORK_CONFIG`     | db-migrate.yml (ECS RunTask awsvpc) |
| `STAGING_NETWORK_CONFIG` | db-migrate.yml                      |
| `PROD_NETWORK_CONFIG`    | db-migrate.yml                      |

GitHub Environments (`dev`, `staging`, `prod`) gate the deploys with required
reviewers configured in the repo settings.

## Failure modes

- **ECR re-tag fails**: most likely cause is the SHA never landed in the
  source repo. Verify via `aws ecr describe-images --repository-name aentro-backend`.
- **`services-stable` wait times out**: open the ECS service events tab; the
  most common cause is a failing task because of a missing secret or a bad
  image. Roll back with the Rollback workflow.
- **Healthcheck fails inside the 5-min window**: promote.yml triggers
  auto-rollback by calling `rollback.sh <env> previous`. Investigate logs in
  CloudWatch (`/ecs/aentro-<env>-backend`).
- **Alembic upgrade fails**: the `db-migrate` job stops the promote workflow
  before any service update happens, so the cluster stays on the prior bundle.
