# PoC ドキュメント レビューチェックリスト

各ドキュメントを最初に通読してから、以下の観点でチェック。

## 共通チェック（全ドキュメント）

- [ ] **読み手特定**: 想定読者（顧客側 IT / 経営層 / 情シス）に最適化された粒度・語彙か
- [ ] **固有名詞**: 「AENTRO」「main プロダクト」など、プロダクト名の表記揺れがない
- [ ] **数字の根拠**: 期間・件数・金額などの数値に「なぜその値か」のロジックが書ける
- [ ] **責任分界**: 自社が何をやるか / 顧客が何をやるか が一目で分かる
- [ ] **次アクション**: 読者が次に何をすればいいか明示されている

## 01. データ依頼書

- [ ] **テーブル単位の網羅性**: `backend/app/models/` の主要エンティティ（Tenant, Store, DailyStoreSales, HourlyStoreSales, LaborActual, Review, Task, ValueCase, Employee, Product 等）に対し、PoC 必須 / 任意 が分かれている
- [ ] **フォーマット指定**: CSV / JSON / Excel など受領形式が明示されている（カラム名・型・サンプルあり）
- [ ] **データ期間**: 何ヶ月分必要かの根拠（KPI 比較・季節性検証など）
- [ ] **マスキング/匿名化**: 個人情報（従業員氏名、レビュー本文内の固有名詞）の取り扱い方針
- [ ] **欠損データの扱い**: 一部テーブルが用意できない場合の代替策・PoC スコープ縮小ライン
- [ ] **受領後フロー**: 受け取ったデータがどう取り込まれ何日で反映されるか
- [ ] **`docs/data_contracts/` との整合**: 既存のデータコントラクト定義（あれば）と矛盾しない

## 02. 8週間 PoC 運用台本

- [ ] **週次マイルストーン**: 1〜8週で「成果物」と「Go/No-Go 判定基準」が定義されている
- [ ] **キックオフ条件**: Week 1 開始のための前提条件（契約、データ受領、環境準備）が明示
- [ ] **役割定義**: 自社側（PM / エンジニア / CSM）と顧客側（PoC オーナー / IT 担当 / エンドユーザー）の責務マトリクス
- [ ] **会議体**: 週次定例の頻度・アジェンダ・参加者
- [ ] **成果指標 (KPI)**: PoC 成功 / 失敗の判定指標（採用率、KPI 改善幅、ユーザー定着度など）
- [ ] **リスク管理**: データ未到着、機能不足、ユーザー離脱などの主要リスクと対応策
- [ ] **本契約への移行条件**: PoC 後の本番化 / 解約判断のクライテリア
- [ ] **プロダクト現状との整合**: `backend/app/api/v1/` が空など、未実装部分のスケジュールが現実的か

## 03. セキュリティ説明書

- [ ] **データフロー図**: 顧客環境 → 自社環境 → 解析 → 結果返却 のフローが図示
- [ ] **保存場所**: PoC データの保管場所（リージョン、暗号化、保持期間、削除タイミング）
- [ ] **アクセス制御**: 誰がデータにアクセスできるか（自社の役職別、顧客側の権限分離）
- [ ] **通信経路**: HTTPS / VPN / SFTP など、データ受け渡しの方式
- [ ] **マルチテナンシー**: `tenant_id` ベースの分離が説明されている（`AccessScope` の言及）
- [ ] **認証方式**: JWT / SSO / 2FA など PoC 期間中の認証方式
- [ ] **インシデント対応**: 漏洩 / 不正アクセス検知時の通知フロー（時間 SLA を含む）
- [ ] **法令対応**: 個人情報保護法、業界基準（PCI DSS など該当すれば）への適合
- [ ] **PoC 終了後**: データ削除証跡、契約終了時の手続き
- [ ] **既知の制約**: 現時点で未実装のセキュリティ機能（パスワードハッシュ、TLS、レート制限等）と PoC 期間中の代替策が明示
