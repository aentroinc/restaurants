# Enterprise Security & Data Handling Brief
# 外食チェーン経営OS セキュリティ・データ取扱説明書 v1

## 0. この資料の目的

本資料は、外食チェーン経営OSのPoCおよび本導入において、顧客企業の情シス、法務、経営企画、監査、経営陣に対して、データ保護、アクセス制御、AI利用、監査ログ、データ削除、障害対応の方針を説明するための資料である。

本資料は、正式なセキュリティチェックシートへの回答前に、プロダクトの基本的なデータ取扱方針を共有する目的で利用する。

---

# 1. 基本方針

## 1.1 データ取扱の原則

本プロダクトは、顧客企業のPOS、勤怠、会計、原価、店舗マスタ、商品マスタ、SV巡回、販促、レビュー等の業務データを取り扱う。

取り扱いにあたり、以下を基本方針とする。

1. 顧客データは顧客ごとに論理的に分離する
2. 顧客データを他社に共有しない
3. 顧客データをモデル学習に利用しない
4. PoCでは原則として個人情報を受領しない
5. 必要最小限のメンバーのみアクセス可能にする
6. すべての重要操作を監査ログに記録する
7. 顧客からの要請に基づきデータ削除できる
8. AI回答には参照データと権限チェックを適用する

## 1.2 顧客に説明する一文

> 御社からお預かりするデータは、PoCおよび契約目的の分析・可視化・レポート生成にのみ利用し、外部への共有やAIモデルの学習には使用しません。アクセス権限、監査ログ、データ削除手順を定め、顧客ごとに分離して管理します。

# 2. 取り扱うデータ

## 2.1 想定データ

| データ | 内容 | 個人情報リスク |
|---|---|---:|
| 店舗マスタ | 店舗名、住所、ブランド、地域、SV | 低 |
| 商品マスタ | 商品名、価格、カテゴリ、原価 | 低 |
| POS売上 | 売上、客数、商品別売上、時間帯別売上 | 低〜中 |
| 勤怠/人件費 | 労働時間、人件費、従業員ID | 中 |
| 店舗別PL | 売上、原価、人件費、利益 | 低 |
| 仕入/在庫/廃棄 | 食材、仕入先、廃棄量 | 低 |
| 販促 | クーポン、キャンペーン、広告費 | 低〜中 |
| レビュー/クレーム | 評価、コメント、店舗 | 中 |
| SV巡回 | 訪問記録、指摘事項、写真 | 中 |
| 改善タスク | 担当者、期限、対応内容 | 中 |

## 2.2 PoCで原則受領しないデータ

- 顧客氏名
- 顧客電話番号
- 顧客メールアドレス
- 顧客住所
- 従業員住所
- 従業員電話番号
- 従業員マイナンバー
- 従業員銀行口座
- 採用/評価/懲戒情報
- 医療/健康情報

## 2.3 匿名化推奨データ

| データ | 推奨処理 |
|---|---|
| 従業員ID | 仮名ID化 |
| 店長ID | 仮名ID化 |
| SV ID | 仮名ID化 |
| 会員ID | ハッシュ化または除外 |
| レビュー本文 | 個人名/電話番号/メール除去 |
| 写真 | 人物が写る場合は原則除外またはマスキング |

# 3. データ保存と分離

## 3.1 テナント分離

顧客データはtenant_id/company_idにより論理分離する。

原則：

- すべての主要テーブルに company_id を持たせる
- APIは認証ユーザーのcompany_idで自動フィルタする
- 他社company_idを指定してもアクセスできない
- 管理者用アクセスも監査ログ対象にする

## 3.2 環境分離

| 環境 | 用途 | 顧客データ |
|---|---|---|
| local | 開発 | 原則ダミーデータのみ |
| staging | 検証 | 匿名化/サンプルデータのみ |
| production | PoC/本番 | 顧客データあり |

本番顧客データをlocal環境にコピーしない。

## 3.3 保存場所

顧客ごとに以下を管理する。

- データ保存リージョン
- データベース
- オブジェクトストレージ
- バックアップ先
- ログ保存先
- データ保持期間

## 3.4 暗号化

最低要件。

| 対象 | 方針 |
|---|---|
| 通信 | TLS |
| データベース | 保存時暗号化 |
| オブジェクトストレージ | 保存時暗号化 |
| バックアップ | 暗号化 |
| シークレット | 環境変数/Secret Managerで管理 |

# 4. アクセス制御

## 4.1 認証

PoC初期：

- メール/パスワード
- 強固なパスワードポリシー
- 必要に応じて2FA

本導入：

- SSO/SAML/OIDC対応
- 顧客IdP連携
- 退職/異動時のアクセス停止

## 4.2 権限モデル

RBAC + ABACを採用する。

### RBAC

| ロール | 権限 |
|---|---|
| Executive | 全社/ブランド/地域の閲覧 |
| Finance | PL/財務KPI閲覧 |
| Operations Director | 店舗運営データ閲覧/タスク管理 |
| SV | 担当地域/担当店舗のみ閲覧 |
| Store Manager | 自店舗のみ閲覧 |
| Product Manager | 商品/原価/メニュー分析閲覧 |
| Marketing Manager | 販促/顧客体験分析閲覧 |
| Admin | ユーザー/権限/データ管理 |
| Auditor | 監査ログ閲覧 |

### ABAC

属性ベースの制御。

- company_id
- brand_id
- region_id
- store_id
- department
- role
- data_classification

## 4.3 店長/SVの制限

店長は原則として自店舗のみ閲覧可能。

SVは担当店舗/担当エリアのみ閲覧可能。

見せないデータ例。

- 他店舗の詳細PL
- 他店長のパフォーマンス詳細
- 個人賃金
- 全社財務
- 役員向けサマリー

## 4.4 自社メンバーのアクセス

自社メンバーの顧客データアクセスは最小限にする。

| 役割 | アクセス |
|---|---|
| Engagement Lead | 必要範囲のみ |
| Data Engineer | データ取込/品質確認に必要な範囲 |
| Analytics Lead | 分析に必要な範囲 |
| Developer | 原則ダミーデータ、必要時のみ限定アクセス |
| Support | 顧客依頼時のみ |

本番顧客データへのアクセスは監査ログ対象。

# 5. 監査ログ

## 5.1 記録対象

以下は必ずログに残す。

- ログイン/ログアウト
- ログイン失敗
- データ閲覧
- ダッシュボード閲覧
- レポート出力
- CSV/PDF/PPTX出力
- AI質問
- AI回答生成
- 参照データ
- タスク作成/編集/削除
- ユーザー追加/削除
- 権限変更
- データ取込
- データ削除
- マスタ変更
- 管理者アクセス

## 5.2 ログ項目

| 項目 | 内容 |
|---|---|
| timestamp | 操作日時 |
| user_id | 操作者 |
| company_id | 顧客企業 |
| action | 操作種別 |
| resource_type | 対象種別 |
| resource_id | 対象ID |
| ip_address | IP |
| user_agent | ブラウザ/端末 |
| success | 成否 |
| metadata | 詳細 |

## 5.3 保持期間

PoCでは最低6か月。 
本導入では顧客要件に応じて1〜7年を検討。

# 6. AI利用方針

## 6.1 AIができること

AI Analystは以下を支援する。

- 店舗別利益悪化の説明
- KPI異常の要因分解
- SVが見るべき店舗の提案
- 経営会議論点の整理
- 改善タスク案の生成
- レポート文面の下書き

## 6.2 AIがしてはいけないこと

AIは以下を行わない。

- 顧客データをモデル学習に利用する
- 権限外データを参照する
- 人事評価や処分を自動決定する
- 価格改定や発注を自動実行する
- 法務/労務判断を断定する
- 根拠のない断定をする
- 個人情報を不必要に表示する

## 6.3 AI回答の分類

AI回答は以下を分けて表示する。

| 区分 | 説明 |
|---|---|
| 事実 | データに直接存在する数値 |
| 計算 | KPI定義に基づく算出結果 |
| 仮説 | データから推定される原因 |
| 推奨 | 人間が判断すべきアクション案 |

## 6.4 AI回答テンプレート

```text
結論:
根拠データ:
原因仮説:
推奨アクション:
期待インパクト:
注意点:
```

## 6.5 AI監査ログ

AI質問ごとに以下を保存する。

- 質問文
- 回答文
- 参照した店舗/ブランド/期間
- 使用したKPI
- 回答生成日時
- ユーザーID
- タスク化したか
- 会議資料に追加したか

# 7. データ取込時の安全設計

## 7.1 Ingestion Sandbox

顧客データは、いきなり本番分析テーブルに投入しない。

流れ。

1. Raw Zoneに保存
2. Sandbox Tableに読込
3. Schema Mapping
4. Data Quality Check
5. Reconciliation
6. Customer Confirmation
7. Canonical Modelへ昇格
8. Analytics Mart生成

## 7.2 Data Quality Gate

以下に該当する場合、自動昇格しない。

- 必須カラム欠損
- 店舗コード不一致率が5%以上
- 商品コード不一致率が10%以上
- 売上合計差異が1%以上で説明なし
- 日付形式エラーが大量発生
- 対象期間の欠損が10%以上
- 個人情報らしき文字列が大量に含まれる

## 7.3 Reconciliation

顧客の元データと取り込み後の数値を突合する。

突合対象。

- 日次売上
- 月次売上
- 店舗別売上
- 商品別売上
- 人件費
- 原価
- 営業利益

差異はレポート化し、顧客確認後に分析へ使う。

# 8. データ保持・削除

## 8.1 保持期間

PoCデータ保持期間は契約で定める。

推奨。

| データ | 保持期間 |
|---|---|
| Raw受領データ | PoC終了後30〜90日 |
| 変換済みデータ | PoC終了後30〜90日 |
| レポート | 契約に従う |
| 監査ログ | 最低6か月 |

## 8.2 データ削除

顧客から削除依頼があった場合、以下を削除対象とする。

- Raw files
- Sandbox tables
- Canonical tables
- Analytics marts
- Object storage files
- Report exports
- AI query logsの顧客データ部分

## 8.3 削除証跡

削除後、以下を記録する。

- 削除対象
- 削除日時
- 削除実行者
- 削除確認者
- 残存データの有無

# 9. バックアップ・障害対応

## 9.1 バックアップ

本導入時の推奨。

- DB日次バックアップ
- オブジェクトストレージのバージョニング
- 設定/マッピング定義のバックアップ
- 復旧手順の定期確認

## 9.2 障害区分

| 区分 | 例 | 対応 |
|---|---|---|
| Sev1 | 全ユーザー利用不可 | 即時対応、顧客通知 |
| Sev2 | 主要画面利用不可 | 当日対応 |
| Sev3 | 一部機能不具合 | 計画対応 |
| Sev4 | 軽微な表示不具合 | 次回リリース対応 |

## 9.3 顧客通知

重大障害時は以下を通知する。

- 発生日時
- 影響範囲
- 暫定対応
- 復旧見込み
- 原因
- 再発防止策

# 10. セキュリティレビュー想定質問と回答

## Q1. 顧客データをAIモデルの学習に使いますか？

使いません。顧客データはPoCおよび契約目的の分析、可視化、レポート生成、AI回答生成にのみ利用します。モデル学習には利用しません。

## Q2. 個人情報は必要ですか？

PoCでは原則不要です。従業員、店長、SVなどは匿名化IDで十分です。顧客氏名、電話番号、メールアドレス等は提出不要です。

## Q3. 他社データと混ざりませんか？

顧客ごとにcompany_id/tenant_idで論理分離し、APIレイヤーとDBレイヤーでアクセス制御を行います。

## Q4. 誰がデータにアクセスできますか？

顧客側の許可されたユーザーと、自社側のPoC担当者のうち必要最小限のメンバーのみです。アクセスは監査ログに記録します。

## Q5. PoC終了後にデータ削除できますか？

できます。契約で定めた保持期間終了後、または顧客要請に基づき削除し、削除証跡を残します。

## Q6. AIは間違った回答をしませんか？

AI回答は、事実、計算、仮説、推奨を分けて表示します。重要な意思決定は人間承認を前提とし、AIの回答には参照データを表示します。

## Q7. 店長が他店舗のPLを見られますか？

見られません。店長は自店舗のみ、SVは担当店舗のみなど、役割と担当範囲に基づいて権限を制御します。

## Q8. データはどこに保存されますか？

契約時に合意したクラウド環境/リージョンに保存します。PoC時点では利用環境を明示し、必要に応じて顧客要件に合わせます。

## Q9. データの持ち出しは制御できますか？

レポート出力、CSV出力、PDF/PPTX出力は権限で制御し、すべて監査ログに記録します。

## Q10. 情シスのチェックシートに回答できますか？

可能です。本資料は概要説明であり、正式なチェックシートには個別に回答します。

# 14. 最終方針

このプロダクトは、外食チェーンの経営判断に深く関わるため、単なるダッシュボード以上に、データ保護、権限管理、監査、AIガバナンスが重要になる。

顧客に対しては、以下を明確に伝える。

> データは安全に預かる。  
> AI学習には使わない。  
> 権限外には見せない。  
> 重要操作は記録する。  
> PoC終了後は削除できる。  
> 経営判断に使う数値は、元データと突合して説明できる。

この方針があることで、経営陣だけでなく、情シス・法務・監査部門を通過しやすくなる。
